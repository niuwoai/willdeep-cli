## 问题与行为变化

原门禁以完整命令字符串记账。`cargo test -p willdeep-cli …` 因包名不存在退出 101，随后 `cargo test -p willdeep …` 虽然通过，仍不能解除旧命令的失败。旧失败随未完成检查点恢复，使之后的回合继续追着错误命令跑。

修复将明确的 Cargo 包选择器错误记为 `invocation_error`：它保留尝试与诊断，不算一次实际验证，也不能产生通过证据。只有在同一工作目录保留测试筛选、features 及全部其他参数，仅纠正一个包选择器，并在当前稳定快照通过，才能解除该项。无关成功、真实编译或断言失败、超时、失效快照及配置的强制检查不会被替代。

诊断分类同时要求命令、退出码 101 和标准包选择错误匹配；兼容标准颜色序列、单行 Cargo 警告、完整的非根包 profile 配置警告及精确的宿主提示后缀。多行警告必须是原生标题及顺序固定的两行 Cargo.toml 路径，不忽略任意前缀；缺行、未知控制序列和混合失败输出均拒绝。Runtime Diff 审计将新状态兼容投影为 `launch_failed`，不会显示为通过。

## 旧检查点兼容

只对未完成检查点、完整的原生持久历史进行自动重新分类。调用和结果必须身份唯一、顺序与角色正确；仅根工作目录、前台 `run_command` 的标准结果可作为证明。同命令所有尝试必须都明确属于调用错误。缺结果、重复 ID、未知结果、真实失败及后台旧记录保留失败。

手动压缩、已物化摘要或导入的历史不自动迁移，避免用新调用错误的次数抵消已丢失的真实失败。自动摘要只改变请求投影，保留原文，因此不影响这类取证。恢复读取不直接写盘；下一次正常检查点保存才持久化新状态。

今天的真实问题样本已只读核对：原文仍在，41 次命令调用的参数结构符合迁移要求；两次坏包名调用及对应结果符合严格分类，纠正命令仅改变包选择器。未输出用户消息正文、凭据或完整会话内容，也未修改会话 JSON。

## 分离式后台验证

生产 Harness 使用分离式后台作业，原路径在启动后直接返回，终态没有写验证账本。本次补上启动快照、终态观察器与输出读取共用的收集入口；启动本身不是证据，重复读取不重复计数。

作业身份和已观察结果写入私有 `verification.json`。已确认的稳定结果可恢复；丢失结束快照、终态缺失或不一致、运行期间快照变化均不能通过。Runtime 重启前尚未观察结束的作业，即使之后退出 0，也记为 `invalidated`，要求重新验证。后台进程仍能跨 Runtime 重启存活。后台验证使用整个工作区快照，因此无关文件变化也可能保守失效。
