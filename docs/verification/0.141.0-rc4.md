## 确定性复现

固定原始提交快照到专用 Docker volume，使用 `rust:1.94.1-bookworm`，限制 3 CPU / 5 GiB 内存，挂载 256 MiB 的 `/fixture-tmp` tmpfs，设置 `TMPDIR=/fixture-tmp`；测试启动命令有 1200 秒上限。未继承宿主用户目录或凭据，未修改全局 Git 配置。

实测根目录设备号为 49、临时挂载点为 83。`git -C /fixture-tmp rev-parse --show-toplevel` 返回 128，stderr 为：

```text
fatal: not a git repository (or any parent up to mount point /)
Stopping at filesystem boundary (GIT_DISCOVERY_ACROSS_FILESYSTEM not set).
```

原实现仅识别 `fatal: not a git repository (or any of the parent directories): .git`。同一原始源码下，两项目标各自独立运行均失败，无需并发：

| 原始测试 | 结果 | 证据 |
|---|---|---|
| `harness::verification::tests::snapshots_distinguish_plain_workspaces_repositories_and_broken_git_metadata` | 0 passed / 1 failed | 原第 35 行，`Git workspace discovery failed` |
| `daemon::mobile_gateway::tests::mobile_configuration_catalog_persists_and_reaches_the_actual_turn` | 0 passed / 1 failed | 原第 1404 行，failed 对 completed，failure_domain=harness |

仅增加手机测试失败诊断、保留原 discovery 实现后，进一步得到：

```text
error=cannot capture verification snapshot: Git workspace discovery failed
model_request_captured=false
```

该错误来自 Agent 请求主模型前获取验证基线的阶段。保持原二进制不变，仅对子进程设置 `GIT_DISCOVERY_ACROSS_FILESYSTEM=1`，两项各 1 passed、0 failed。这个开关仅用于因果对照，未写入实现或 CI。

在可写且独立挂载的 Linux 临时目录中可复验，先确认 `TMPDIR` 的设备号和 Git 原始诊断；命令中的环境变量只作用于新测试进程，不在并发 Rust 测试中修改环境：

```bash
TMPDIR=/dev/shm cargo test --locked -p willdeep --bin willdeep harness::verification::tests::snapshots_distinguish_plain_workspaces_repositories_and_broken_git_metadata -- --exact --nocapture
```

```bash
TMPDIR=/dev/shm cargo test --locked -p willdeep --bin willdeep daemon::mobile_gateway::tests::mobile_configuration_catalog_persists_and_reaches_the_actual_turn -- --exact --nocapture
```

macOS 原始两项目标均通过；原始完整 CLI 以 8 线程运行，1249 passed、0 failed、4 ignored，192.22 秒。这说明本机普通临时目录下的并发通过不能否定挂载边界缺陷。

## 修复范围

- 精确接受 Git 的两种已知“发现范围内没有仓库”诊断。继续拒绝损坏 gitfile、无效显式 Git 目录、权限、所有权等错误；不把所有 128 或宽泛的 `not a git repository` 当作成功。
- 不改变 Git 的父目录查找范围，不给普通目录 fixture 初始化仓库，不增加重试或延长超时。
- discovery 失败保留退出状态及最多 2048 字符的脱敏 stderr；先移除可能携带 userinfo 或查询凭据的完整 URL，再使用现有凭据脱敏，最后按 Unicode 字符截断。进程启动失败保留原生错误。任务仍然失败，不吞最终错误。独立审阅发现初稿通用脱敏不覆盖 URL userinfo，已补齐实现及回归。
- 手机测试保留公共任务状态、实际 HTTP 请求、模型及技能持久化的所有断言；失败时追加脱敏限长的内部错误及请求是否发出，不扩展公共 DTO。
- 分类回归覆盖两种非仓库诊断，以及无效 gitdir、损坏 gitfile、权限、所有权、空 stderr 的负例。真实 Git 测试保留普通目录、初始化仓库、损坏 `.git`、删除目录四种状态。
- 版本清单、内部依赖版本钉及当前文档同步到 `0.141.0-rc4`；Cargo.lock 仅变更四个本地包版本。未修改 supervisor/PID 修复。

## 已检查的隔离问题

目标测试均使用 UUID 临时目录；手机端口由系统分配，模型目录缓存键包含独立 home。未发现 Rust 测试修改全局 cwd、PATH 或 GIT_*。Core 与 CLI 的单元测试在不同进程，Core 环境写入不能反向改变 CLI 进程。

另确认 Web 路径展开测试永久修改进程 HOME 且没有隔离，实际模型执行也允许通用 `WILLDEEP_API_BASE` / `WILLDEEP_API_KEY` 覆盖 fixture 档案。这些属于隔离缺口；本次未发现它们触发原目标失败的证据。在隔离 Linux 进程中无需这两类条件即可复现和修复两项目标，故未扩大本次变更去重构配置解析或 Web 路径展开。
