# q4 Qwen3.6-35B-A3B：96K 单路部署与 72K 冷热对比

测试日期：2026-11-04。原始记录使用 UTC；主测速于 12:47:00 UTC（北京时间 20:47:00）完成，随后完成服务与 API 冒烟检查。

## 结论

q4 已切换为 **Qwen3.6-35B-A3B UD-Q2_K_XL，96K 单路**。服务保持运行，实际模型、单槽上下文、聊天、工具调用往返及 JSON 输出均通过检查。

另于 12:50:57 UTC 经 `https://q4.niuwoai.com` 公网域名完成 `/health` 和鉴权聊天检查，实际返回新模型及 `OK`。该请求由 q4 发起，只证明域名链路可用，不代表用户所在网络的延迟或吞吐。

与此前 Qwen3.8-27B UD-IQ3_XXS 的同口径数据相比，全新 72K 输入的 prefill 从 **1,000.7 → 1,507.2 tok/s（1.51 倍）**，decode 从 **26.33 → 70.01 tok/s（2.66 倍）**。首个非空输出等待从 **73.69 → 48.93 秒**，减少约 **33.6%**。

本轮确认了 **64K 前缀缓存可复用**：新增 8K 输入的首个非空输出等待为 **6.18 秒**；完整 72K 输入重复时为 **0.053 秒**。这些结果依赖已建立的相同前缀，不能套用到全新任务。

输出速度改善明显，但每次从零处理全新 72K 输入仍需约 49 秒。对连续追加上下文的会话更有帮助；若每个新子代理都携带全新的 72K 材料，输入等待仍然较长。

## 与旧 27B 对比

旧结果见 [Qwen3.8-27B 测试报告](../q4-qwen38-96k-2026-11-04/README.md)。两轮使用同一台 GPU、同一 llama-server 二进制、相同上下文和并发、相同输入 token ID 数组及 512 tokens 输出限制。

| 条件 | 旧 27B Prefill | 新 35B-A3B Prefill | 旧 27B Decode | 新 35B-A3B Decode | 旧首个输出（秒） | 新首个输出（秒） |
|---|---:|---:|---:|---:|---:|---:|
| 冷 KV，全新 72K | 1,000.7 | **1,507.2** | 26.33 | **70.01** | 73.69 | **48.93** |
| 热 GPU，无 KV | 1,000.6 | **1,508.3** | 26.29 | **69.91** | 73.87 | **48.97** |
| 64K 缓存 + 8K 新输入 | 732.6 | **1,328.5** | 26.29 | **69.55** | 11.20 | **6.18** |
| 完整 72K 重复 | — | — | 26.27 | **69.77** | 0.105 | **0.053** |

吞吐单位为 tok/s。冷请求总耗时由 **93.09 → 56.20 秒**，减少约 **39.6%**；64K 缓存条件的总耗时由 **30.63 → 13.53 秒**，减少约 **55.8%**。

这次同时更换了模型架构和量化（旧 `UD-IQ3_XXS`，新 `UD-Q2_K_XL`），不能把全部提速归因于 MoE 或缓存架构。测试不证明两种量化下的回答质量相同。

## 方法与口径

1. 使用 q4 本机 loopback 的 llama.cpp 原生 `/completion` 接口测速，排除公网隧道传输延迟。
2. 使用合成 Rust 风格记录，通过新模型自己的 `/tokenize` 重新生成精确 token ID 数组。头部 45 tokens、尾部 33 tokens，合计严格为 73,728。新旧模型生成的输入数组 SHA-256 完全相同；输入不含用户源代码。
3. ChatML 输入包含显式闭合的 thinking 前缀。请求使用 `temperature=0`、`seed=42`、`n_predict=512`、`ignore_eos=true`；全部输出 token 均计入吞吐。
4. 每轮依次测冷首请求、热 GPU 无 KV、64K 前缀预热后追加 8K、完整输入重复。四个条件均有 3 个正式样本；另有 3 个仅生成 1 token 的 64K 前缀预热样本。旧轮次的完整重复输入组是在九个核心样本之后补测，新轮次为每轮测一次；这一组不是完全同序实验，只作为缓存行为与延迟参考。
5. 冷首请求前重启服务，临时屏蔽原有 `ExecStartPost` HTTP 请求预热。冷测不包含模型加载时间，不清理操作系统文件缓存，也不代表 GPU 断电冷机；llama.cpp 自身的加载/内核 warmup 仍保留。
6. 无 KV 条件通过不同的短前缀请求替换活动槽位，再请求完整 72K；每次均实际核验 `timings.cache_n=0`。前缀组实际核验命中 65,536、重新求值 8,192；完整重复组实际命中 73,724、重新求值 4。
7. 实际缓存命中使用 `timings.cache_n`，实际 prefill 数使用 `timings.prompt_n`，每条正式样本二者之和均为 73,728。顶层 `tokens_cached` 是生成后槽位驻留 token 数，不能当作输入缓存命中数。
8. Prefill 采用 `timings.prompt_per_second`；decode 采用 `timings.predicted_per_second`，本构建公式为 `(predicted_n - 1) * 1000 / predicted_ms`。首个非空输出是客户端收到首个非空 SSE 内容块的墙钟时间。
9. `64K+8K` 的 1,328.5 tok/s 衡量末尾实际计算的 8K，与从头计算完整 72K 覆盖不同位置范围。按整段 72K 折算的约 11,957 tok/s 含缓存免计算部分，不能当作真实 prefill 吞吐。完整重复输入只重算 4 tokens，其短阶段吞吐不用于推断长输入性能。
10. 测试覆盖 72K 输入和 512 输出，没有测试填满 96K 边界，也没有评测复杂编程、长上下文回答正确率或思考模式质量。聊天/工具/JSON 检查仅为小型 API 冒烟验证。
