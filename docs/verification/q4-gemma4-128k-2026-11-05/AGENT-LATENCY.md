## 界面“首答”口径

当前工作树的Runtime路径在第一次收到`type=usage`时调用`record_turn_usage()`，把该事件抵达时刻写为首答；它未使用首个正文增量作为停止点。usage发生在本次模型生成完成之后。因此该字段不是严格的首字符耗时。

- [runtime_ui.rs](../../../crates/willdeep-cli/src/tui/runtime_ui.rs:576)：usage分支。
- [app_state.rs](../../../crates/willdeep-cli/src/tui/app_state.rs:1034)：首次usage写入首答时间。
- [runtime_ui.rs](../../../crates/willdeep-cli/src/tui/runtime_ui.rs:742)：Runtime收尾没有Core outcome中的精确首正文时间。

现场后两轮正文增量分别在22:29:04、22:29:48已出现，用量事件在22:29:05、22:29:48出现。这个统计口径问题只解释部分显示差值，不能掩盖调用前真实存在的准备等待。Thought标签也仅测从首个思考增量抵达客户端之后的区间。

注意版本边界：正在运行的CLI和daemon为0.143.0-rc7；当前共享源码HEAD为ced9c11b（0.139.0-rc6）且存在其他会话未提交修改。源码用于定位已有路径，不能作为当前安装二进制逐行一致的证明。现场时间和缓存结论来自实际日志与账本。

## 附加请求与处理方向

主回答结束后，每轮还有辅助用途的模型调用。后两轮各有两条，客户端完整耗时约8秒和12—13秒；其服务端生成约7秒和5秒，客户端耗时还含排队，不能直接相加。它们与主模型共用单槽，可能影响后续请求；本次并未证明它们造成了上述准备空档。

建议下一步在同一次回合内加入准备阶段分段计时，优先消除重复的昂贵初始化或扫描；同时让Runtime首答统计绑定首个正文增量，保留用量结算作为无正文时的兜底。辅助调用应避免与新用户请求争用单槽。保留q4现有Gemma、MTP、单路128K配置；现有证据不支持换模型或关缓存来解决这段等待。
