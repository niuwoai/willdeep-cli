# 0.143.0-rc8：Agent 首答延迟修复与验收

日期：2026-11-05。基线：`ca44885b`（0.143.0-rc7）。本次为既有产品迭代，修复在独立工作树完成。

## 结论与适用范围

确认并修复了两项缺陷：子会话协调账本在没有变化时仍反复同步写盘；Runtime TUI 把完整用量事件到达时间算成首答。新增默认关闭的准备阶段诊断，便于继续区分本机准备、模型推理、传输与收尾。

真实 PTY 中，旧版空闲一秒产生 9 次账本提交，修复版为 0；双方均完整保存回复并在正常退出时刷新 Runtime 游标。首答计时回归与真实 PTY 门槛通过。

实际配置的本地执行样本中，修复前从进程启动到 Core 首轮开始为 4.931 秒、到首正文为 7.043 秒；修复后分别为 3.167 秒、4.835 秒。这是存在本机负载与远端输出差异的单轮观测，不构成稳定提速倍数或原截图 10 秒延迟的完整归因。

新版本尚未安装、提交、推送或发布；日用 CLI/daemon 仍保持原版本。q4 的 Gemma 4 12B QAT + MTP、单路、每槽 128K 配置保持不变。

## 原现场的证据

用户原截图的三轮首答为约 13.82 / 10.82 / 10.30 秒。对应主模型调用的完整客户端耗时为约 6.330 / 2.051 / 2.443 秒，后两轮输入缓存命中约 99.7%。服务端热轮仅新算 48 tokens；不能将 14.4K 输入总量理解为每轮都从头 prefill。

Runtime 秒级事件显示，`task.started` 到 Core `turn_started` 之间约有 5 / 7 / 6 秒。该差值包含准备链路，不能直接归到模型。原 TUI 的“首答”又延后到 `usage`，包含了首正文之后的生成时间。

只读观测还发现：没有任何 assignment 的子会话账本仅 386 bytes，约 1.2 秒内 revision 仍增加 9 次。调用栈采样命中 `append_peer_context → host_context → transaction → persist`，以及控制锁、文件/目录同步落盘。该证据证明空提交造成真实开销，但不能单独解释所有等待。

MCP、Git 验证快照和事件恢复均已单独测量。本次没有移除这些能力，也没有削弱审批、会话执行权、验证基线或恢复保证来换取速度。

## 实现

### 跳过没有内容变化的账本提交

- `ChildStore::persist` 在既有独立控制锁内部，比较磁盘持久字节与当前账本的规范序列化字节。
- 内容相同且本实例已成功为该内容完成文件/目录同步，才直接返回；不递增 revision 或原子替换。
- 内容相同但持久性未确认时仍同步一次：新实例重新建立持久性，失败后的重试不能以页缓存中相同的字节冒充已完成屏障。
- 内容变化时仍递增 revision，写临时文件、原子替换，并同步文件与父目录。只有屏障成功后才保存内容摘要作为后续免同步的依据。
- 保留所有显式提交屏障的位置，真实结果、唤醒身份等仍先持久化，再调度或唤醒。
- reconciliation 只有在任务状态或错误发生变化时才更新 `updated_at`，避免轮询本身制造修改。
- 缺失文件仍初始化；读取错误保留上下文并返回，不以“无变化”吞掉错误。

### 首答计时与累计用量分开

- 首个非空 `assistant_text_delta` 到达时固定首答；空字符串、单独 reasoning 不触发。
- 非流式完整正文与纯工具响应的 `usage` 保留兜底；不报告 usage 的纯工具响应可在完整模型响应后的 `tool_requested` 计时。后续增量、用量和模型轮次不重置首答。
- 提交入口保存单调时钟，包含本次准备、提交请求及 Turn 回执补查的等待；提交期间已产生的正文可正常计时，不按秒级墙钟拒收。
- 以提交时 Runtime 事件头与返回的 Turn/Task 身份判断归属；排队回执尚无 Task 时，通过现有 `queued_user_message.turn_id` 绑定。旧终止事件不能清掉新轮时钟，异属 Task 输出不进入本轮投影。
- 普通重连与快照可恢复运行态，但不能授予新的首答计时资格；同一秒内的历史回放也不产生近零首答。本地执行继续优先使用 Core 报告的值。
- 这是 TUI 进入本次提交之后到收到正文的耗时，包含准备、排队、传输及思考；并非纯模型 prefill，也不包含收到正文之后到首次屏幕绘制的延迟。

### 可选准备阶段诊断

`WILLDEEP_TRACE_PREPARATION=1` 开启 `willdeep.preparation.v1` JSON 日志，默认关闭，仅输出固定 component/stage、`elapsed_ms` 与 `total_ms`，不记录消息、配置、工作区路径或凭据。

覆盖 `runtime_dispatch`、`workspace_checkpoint`、`harness`、`runtime_execution`、`turn_persistence`、`agent_preflight` 与首轮 `agent_context`。阶段耗时是相邻标记之差；嵌套组件累计值不能直接相加。Runtime 的日志由 daemon 的 stderr 日志承接；写入失败后停用本次 tracing，不让诊断或 Drop 的 stderr 错误中止任务。

### 隔离 Runtime 路由

使用现有配置路径和独立数据目录，实际出现 `runtime_execution`，验证走了真实 daemon 执行器，执行完已通过该隔离目录的正常入口停止 daemon。该轮从 CLI 冷启动到队列消息为 14.756 秒、Core 首轮开始为 22.842 秒、首正文为 25.100 秒；其中新数据目录初始化的成本不能混入日常已启动 TUI 的每轮耗时。

队列消息到 Core 首轮开始约 8.086 秒，新增分段可解释其中约 7.845 秒：

| 互不重叠的准备组件 | 耗时 |
| --- | ---: |
| Runtime 调度 / 文件回退内容快照 | 5.323 s |
| 会话认领、Harness 与会话绑定 | 1.577 s |
| 消息持久化 | 0.267 s |
| Core 预检 | 0.493 s |
| 首轮上下文 | 0.185 s |

内容快照内部约 5.183 秒（包含在第一项内，不能再相加）：打开影子仓库 1.088 秒，写入内容树与提交 3.902 秒，引用与保留策略约 0.167 秒。它保存实际文件内容，服务于“回到某一步”的文件回退，**不同于此前约 0.3—0.7 秒的 diff 指纹快照**。这段路径位于 Harness 之前，解释了此前分段为什么仍有准备空档。

另一次仅带前一组埋点的隔离冷启动从 CLI 启动到首轮开始为 25.305 秒；这说明等待仍明显波动，不能以本地执行的 4.835 秒首正文宣称 Runtime 已稳定达到同一水平。本次保留内容快照的完整哈希与回退语义，未用关闭快照或降低持久性掩盖成本。

### 本机旧评测进程的竞争

一次进程快照有 142 个 WillDeep 进程，其中 40 个处于 I/O 等待。按实际打开的 stderr 日志，识别出 52 个评测临时目录 daemon：39 个可核对为没有 Runtime 任务、assignment 数为 0，其余 13 个缺少所需元数据而排除。39 个已核对的进程在短观察期间合计仍有 90 次 revision 增加；观察含一秒等待及顺序读取开销，不算成精确每秒速率。

[逐项审核清单](idle-evaluation-daemons.md)记录了这 39 个 PID、评测根、模型、用例与观测提交数。没有停止任何既有评测进程，也没有修改日用 daemon。该环境竞争与旧版无变化写盘缺陷叠加，足以要求先去除已确认的无用负载再重测；尚未进行停止前后对照，因此不声称已证明其导致了全部延迟。
