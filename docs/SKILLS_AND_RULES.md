# 技能与规则

配置页的「技能」分组原先只有一个「技能根目录」文本框：看不到已装了哪些技能，也没法从网上装。规则则只认一个文件 `~/.willdeep/CLAUDE.md`，想叠几套规则就得自己拼进这一个文件。这一版把两边都补上，并按 Xedit 的做法把规则放进提供商能缓存的那一段。

## 技能

技能仍然是「目录 + `SKILL.md`」，发现顺序不变：工作区的 `.willdeep/skills`、`.agents/skills`、`.codex/skills`，用户主目录下的同名三个目录，再加上 `[skills].roots` 里配的额外目录。同名技能先发现的赢。

配置页的「技能」分组现在做四件事：

1. **列出已发现的技能**。每条显示名称、一行说明、档位（worker / standard / deep）和来源目录。这个列表是扫盘得来的，不写进 `config.toml`。
2. **查看与编辑**。打开一个技能就是读它的 `SKILL.md` 全文，改完直接写回这个文件。也可以在用户技能目录里新建、删除。
3. **从 GitHub 安装**。粘一个地址，形如 `https://github.com/拥有者/仓库`、`拥有者/仓库`，或带子目录的 `https://github.com/拥有者/仓库/tree/分支/路径`。安装器拉仓库的代码档案（`codeload.github.com` 的 zip），找出里面的技能目录，拷贝到 `~/.willdeep/skills/<名字>`。同名已存在就拒绝，不覆盖。
4. **额外搜索目录**。原来的 `roots` 文本框留着，用于指向本机已有的共享技能库。

安装器只接受 GitHub。它拒绝凭据、私有仓库和任何不是 `github.com` 的主机；下载限 32 MiB，解压限 64 MiB，单个技能目录限 8 MiB。压缩包里的路径会先清掉 `..` 和绝对路径，落在解压目录外的条目直接丢弃。

这些操作走配置服务的两个新工具：`skills.library`（列出）和 `skills.install`（从地址安装）。查看、编辑、新建、删除是页面直接读写 `SKILL.md` 文件，不经过配置文件。配置服务只在本机回环地址上可写，这一点没变。

技能正文仍然不进系统提示词。系统提示词里只有一份有界的目录（名称、一行说明、档位），模型用 `list_skills` / `read_skill` 按需取正文。

## 规则

规则是每一轮都要遵守的长期约定，不是按需读取的技能。一条规则是一个文件，或一个目录：目录里的 `*.md` 按文件名排序拼接，子目录不扫。

配置在 `[rules]`：

```toml
[rules]
files = [
  "~/.willdeep/rules/agentrules.md",
  "~/.willdeep/rules/team",
]
```

排在前面的先拼进提示词。提示词里写明后面的规则更具体，项目规则比全局规则更具体，用户最新的一句话最具体。优先级是写给模型的一句话，宿主不做文本合并。

没有 `[rules]` 时仍然读 `~/.willdeep/CLAUDE.md`，旧配置不用改。写了 `[rules]` 之后，这个文件就不再自动加进来；要继续用它，把路径写进 `files`。

单个文件上限 256 KiB，全部规则合计上限 512 KiB。超限的部分不拼进去，提示词里留一行说明被截掉了多少，让模型知道规则不完整。读不动的文件同样留一行说明，不让整个会话因为一个文件启动失败。

### 内置的 agentrules

第一次启动、而 `~/.willdeep/rules/` 还不存在时，宿主把内置的规则写到 `~/.willdeep/rules/agentrules.md`，并在没有 `[rules]` 的配置里加上这一条。目录已经存在就什么都不做：不覆盖用户改过的文件，也不把已删掉的规则加回来。

内置的是 [niuwoai/agentrules](https://github.com/niuwoai/agentrules) 的精简版，只留每个主题的 MUST / MUST NOT。这个仓库自己的用法就是不把整库塞进每一轮：项目侧用 `--compact` 只留硬约束，全局用 `--index` 做成路由索引。这里选精简版而不是索引，是因为本仓没有 Xedit 那样的「按文件名读一份内置规则」工具；索引指向读不到的文件，比不如把硬约束直接给模型。精简版的源文件在 `crates/willdeep-core/assets/rules/agentrules.md`，文件头注明对应的仓库版本，升级时按那个版本重新生成。

配置页的「规则」分组列出每一条：启用开关、路径、排序，加上「查看 / 编辑」「从 GitHub 安装」和「恢复内置规则」。启用与排序写回 `[rules].files`；编辑直接改规则文件。

## 提示词怎么拼，以及缓存

提供商按最长公共字节前缀缓存。系统提示词或更早的位置变一个字节，后面的整段历史都失效。所以稳定的东西要放在前面，每轮都可能变的东西要放在后面，两者之间要有一个明确的断点。

系统提示词的顺序：

1. 稳定契约（身份、语气、工具契约、委派契约）加公开工种目录。这一段只随代码版本变，是 `prompt_bundle` 哈希的那一部分。
2. 全局规则。来自 `[rules].files`，或旧的 `~/.willdeep/CLAUDE.md`。只有你改规则文件或改配置时才变，变了就该让缓存失效。
3. 技能目录。同样只在装上、卸掉或改了技能说明时才变。
4. 简洁回复覆盖、插件路由说明。这两段按会话固定，不随轮变。
5. 动态工作区上下文：工作区路径与平台。换一个工作区就变。
6. 项目规则（工作区里的 `AGENTS.md` / `CLAUDE.md`）、验证要求、计划、目标、预算。这些每轮重写，是稳定前缀之后的尾巴。

分界在第 4 段与第 5 段之间。Anthropic 请求把系统提示词拆成两块文本，第一块末尾打 `cache_control: {"type": "ephemeral"}`，第二块不打。这样工作区路径、项目规则或预算数字变了，稳定前缀仍然命中；而规则或技能目录自己变了，前缀就该失效，因为那时模型必须重新读到新内容。其余提供商走自动前缀缓存，同一个顺序对它们同样有效，只是断点由服务端自己决定。

这与 Xedit 的差别只有一处：Xedit 把随当前文件变化的目录规则挂到每轮用户消息上，因为它的规则范围跟着打开的文件走。本仓没有「当前打开的文件」这个概念，项目规则是按工具调用逐步发现的，所以它们留在系统提示词里、放在断点之后。

时间戳不进系统提示词。需要当前时间的地方放在每轮的用户侧上下文里，不在这一版的范围内。
