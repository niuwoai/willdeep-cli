# 首次打开目录的审批模式引导

日期：2026-11-06。产品方向已确认，计划版本为 0.146.0-rc1；本轮仅交付源代码，不包含本机安装、打 tag 或公开发布。独立于 0.145.0-rc3 修复发布。

## 产品决定

首次打开新项目或目录时，帮助用户根据来源与操作风险选择现有审批档位。默认选择“智能审核”；风险较高且用户愿意值守时选择“严格模式”；用户愿意给予更大自主执行权限时，明确选择“完全访问”。

用户已澄清：这是一项现有审批模式的首次使用引导，不新增独立的目录信任状态、信任数据库、授信凭据或用户配对流程。先前关于独立信任门禁的方案已取消。

## 交互

- 展示实际工作目录与标题“选择此目录的审批模式”。来源说明仅帮助选择，不根据仓库名或来源标签自动提高权限。
- 默认焦点/选中项为“智能审核”：按现有规则和智能审核决定放行或询问。
- “严格模式”：按现有严格模式语义，让用户确认需要审批的操作，适合愿意值守的情况。
- “完全访问”：减少操作审批，给予更大自主执行权限；沿用已有升档确认，不因 Enter、超时或初次打开自动选中。
- 提供取消；取消不启动新任务、不切换到新目录。
- 已有“工作区访问”档继续保留在现有权限面板，不删除、不改名，也不改变其审批语义；首次引导重点解释用户指定的三种选择。
- 用户作出的选择直接写入现有工作区/会话审批字段。需要记忆时复用既有权限持久化，不再维护第二个“信任状态”。之后可用现有权限面板、`/permissions` 修改。
- 首次引导优先于该入口的任务执行。非交互运行不增加阻塞式问答，沿用既有显式配置与命令参数；缺省采用现有智能审核语义。
- 已有只读工作区硬上限、FullAccess 的既有保护、子会话权限及模型不能自行升档等边界保持原义。

## 安全语义

审批模式管理写入、命令及外部操作的审核方式。严格模式并不等于“禁止读取项目”或隔离不可信项目内容；本轮不声称提供那类独立隔离。完全访问仍遵循产品现有的必要保护，不将其描述成与其他工具 bypass 模式逐条等价。

本轮不重构 Core 权限执行器、不禁止现有项目规则/Skills/MCP/Hook 加载、不引入独立的 Web 操作者鉴权体系。产品文案使用现有 zh-CN/en/ja 资源，简洁解释用户操作后果。

## 验收

1. 新目录首次交互默认智能审核；Enter、超时、旧默认或来源标签均不能意外升到完全访问。
2. 严格/智能/完全选择落到现有对应审批值；完全访问保留明确确认，取消不提交或切目录。
3. 已明确配置的权限、只读硬上限及既有工作区访问档保持一致；恢复会话不被引导静默覆盖。
4. 已保存的目录选择跨会话保持；用户可通过原有 `/permissions` 或权限面板调整。
5. 非交互入口不挂起，CLI/TUI/Web 三端文案、默认项及实际执行模式一致。
6. 无独立信任 ledger、TrustState、授信 Runtime API、配对秘密或模型可自行升档的入口。

## 实施契约

- 继续使用 `WorkspaceAccess` / `ApprovalMode`，不增加 TrustState 或信任 ledger。
- 既有 `RuntimeWorkspace` 增加 `approval_mode_configured: bool` 作为首次引导的完成标记，仅控制界面是否重复显示，不参与任何权限计算。旧记录缺省为 true 以保留明确选择；新目录自动登记为 Smart + false，用户显式登记/选择后为 true。该标记沿现有 RuntimeWorkspace 协议和 Web summary 传递。
- `crate::daemon::set_remote_workspace_approval_mode` 调用 Runtime 的原子 `workspace.set_approval_mode` 操作，只更新现有 access 与引导完成标记，并保留 name/provider_profile/skills/mcp_servers。该操作与管理员 `workspace.register` 共用同一工作区锁；若并发管理员将目录设为只读，审批选择返回冲突，不会覆盖只读策略。完全访问确认在锁内校验；不引入独立信任或授信 API。
- CLI/TUI 和 Web 都通过此原子操作保存目录选择；新目录选择更新工作区默认审批值，当前会话仍按既有 Session 覆盖、配置与 SharedApprovalMode 语义生效。恢复会话的已有覆盖值不被新目录引导清空。
