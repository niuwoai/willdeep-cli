# Web 聊天错误、子会话提议与待处理入口

日期：2026-11-07

## 背景与范围

这是既有 Web 客户端的交互修复，沿用 React、TypeScript、React Query、现有浅色/深色 token 与中英日文资源。用户反馈：运行失败只有笼统分类；子会话手填表单常驻；Runtime 的“需要处理”计数缺少定位和进入会话的路径。

本轮不改变已有子会话的工作区权限、控制权、依赖、订阅或运行时隔离规则，也不接触正在执行的生产任务。实现与验收使用独立 worktree、私有临时 HOME 和本地确定性 Provider。

## 交互要求

### 具体错误原因

运行失败时显示可理解、可定位问题的原因，实时失败和重新打开历史会话保持一致。优先使用服务器提供的、已脱敏的具体原因；没有详情时才回退到既有分类文案。不能为了显示原因把内部错误对象、凭据、命令参数或完整本地路径直接下发给浏览器。

### 从聊天生成子会话提议

没有提议或已有子任务时，聊天页不渲染常驻的“发起子会话”表单及其空状态。用户在聊天中明确要求创建子会话后，由聊天上下文生成完整提议，包括标题、任务简报和必要的执行选项；不使用前端关键词匹配推断用户授权。

提议卡应让用户看懂要做什么，主要操作为“开始”，无需重复填写已在聊天中表达的信息。点击前不启动子任务；开始期间显示进行状态并防止重复提交，失败保留提议与可理解的原因。已有子会话继续提供状态、结果和打开对应聊天的入口。确认开始不应意外切换当前聊天或清空草稿。

### 待处理会话导航

Runtime 侧栏的“需要处理”在存在可处理事项时可通过鼠标和键盘操作。激活后定位并聚焦到待处理会话区域，列出授权范围内的会话标题与待处理原因；点击标题进入对应会话。

计数与列表必须使用一致的数据口径，不把缺少关联会话的条目导航到错误会话。空状态、加载失败、会话已删除或不再需要处理应有明确反馈。切换会话继续遵守现有聊天流与草稿保护规则。

## 实现决策

- Runtime 根据持久 Turn 来源识别 Web 的 `start_session`，在子会话账本增加兼容旧记录的 `proposals` 集合。提议生成不占执行槽；用户确认时使用保存的参数和稳定派生请求标识，执行既有准入检查。关闭与开始使用同一事务锁，不引入另一套任务执行状态。
- Web 提议卡通过 React Query 轮询，开始或关闭只发送提议 ID 与请求 ID；没有提议和已有任务时隐藏空面板。正常聊天是否调用工具由宿主契约约束，不靠浏览器关键词猜测。
- 错误详情使用统一安全投影；待处理会话按授权项目归属和最新轮次去重。忙碌或有文字、附件草稿时新标签打开目标会话，空闲且无草稿时原页切换。

## 验收重点

- 真实 Runtime 的失败原因能在即时提示和历史恢复中看到，敏感内容不进入 Web DTO。
- 普通聊天没有子会话创建卡；明确创建请求产生预填提议；点击开始只产生一次任务，已有子会话仍可打开。
- 多会话待处理数据可列出，点击计数定位列表，再点击标题进入正确会话；空列表和过期条目行为明确。
- 覆盖中英日资源、键盘操作、窄屏和既有浅/深色样式。
- 执行相关原生单元测试、Web 测试与构建，以及隔离浏览器交互验收；实现完成后同步版本、CHANGELOG 和使用说明。
