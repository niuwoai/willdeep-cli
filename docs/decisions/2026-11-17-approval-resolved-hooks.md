# 审批结果 Hook：复用真实裁决链

> 日期：2026-11-17。目标版本：0.150.0-rc3。既有 Runtime 的接线修复，对应 [Pi / OMP 差距分析](../research/2026-11-17-willdeep-cli-gap-analysis.md) P1「验收证据与审计接线」中的 `approval_resolved` 子项。实现与验收记录分开保存，不以本决策代替测试结果。

## 范围与顺序

P0 的文件版本、多文件预览/应用、查询型 LSP 与固定任务基线已在 rc1 实现，验收归档于 [rc2 P0 记录](../verification/0.150.0-rc2/p0-coding-tools.md)。真实 Rust 语言服务和 Windows 原生运行仍缺本机证据；不自动安装服务，也不把交叉编译当原生验收。

本轮先清理三处 CLI Clippy 阻塞，随后补已有配置可声明、但未投递的 `approval_resolved`。这一步复用 Hook 注册表与审批报告入口，不建立另一套权限系统或审计队列。

后续顺序按依赖推进：查询型 LSP 之上的语义重命名与 AST 搜索、受控浏览器集成、独立 BYOK 搜索、覆盖各辅助调用的项目模型策略，以及绑定执行和快照的 Goal 验收证据。各自需要独立契约与验收；本轮审批 Hook 不表示这些能力已完成。

## 裁决与投递契约

- 事件来自共享工具执行链中实际返回的审批器决定，以及判官的最终放行。`source=approver` 表示审批器返回结果，不等同于人工批准：无人交互、通道关闭或取消也可能返回 `Deny`。判官放行标为 `source=judge`；判官拒绝或不可用后转人工时，仅投递审批器最终返回的决定。
- 审计事件发生于裁决后，不能修改或推翻审批结果。`pre_tool` 仍是可以拦截的工具前置 Hook，`approval_resolved` 是结果观察点。
- 投递使用现有 `HookRegistry`、命令超时、载荷上限及凭据脱敏规则。没有配置相应 Hook 时保持快速返回。
- 审批器结果的 `tool` 使用审批请求动作名，判官放行命令时为 `run_command`；动作名与 `detail` 均脱敏，后者复用 `with_tool()`。`session_id` 与 `workspace` 来自 Registry；来源放在 `extra.source`，投递时的审批模式放在 `extra.mode`。审批器结果为 `allow_once`、`always_allow`、`deny`，判官放行为 `allow`。不猜测缺失的工具调用身份，不复制任意模型正文。
- 载荷先按字段裁剪，再序列化为不超过 16 KiB 的合法 UTF-8 JSON，并标注截断。任意额外字段和多字节内容也受总预算约束，不能在序列化后的 JSON 字节串中间截断。
- 相同的实际裁决不能因为 Runtime 反馈或 UI 更新被重复投递。不同阶段确实重新裁决时，各自保留真实事件。
- Hook 失败不把拒绝变成允许，也不把允许变成拒绝；既有 Hook 失败处理负责报告执行问题。
- 审批报告不能证明工具已执行、命令成功或文件已写入。执行结果仍由工具回执、Job 和验证证据提供。

## 取消与保证边界

Hook 在当前调用链内等待，沿用现有超时。取消或进程退出可能中断尚未完成的投递，不承诺可靠队列、恰好一次或崩溃后补发。投递不是执行授权，不因重试 Hook 自动重放工具。

静态放行、缓存白名单命中、FullAccess 免审和硬拒绝不凭空补造审批器结果。`ask_user` 的答案属于问答，不当作工具执行授权。`AlwaysAllow` 事件只表示审批器返回该决定，不证明授权已成功持久化；后续写入白名单失败仍按既有逻辑返回失败。委派只读会话继续不继承宿主 Hook。人工拒绝与取消的精确来源仍以 Runtime 反馈账本为准。

## 验收要求

单元与执行入口测试使用隔离工作区和本地合成 Hook，不调用外部服务或真实模型。覆盖允许、拒绝、判官裁决/回落人工、自动规则、未知副作用重试保护，以及 Hook 非零退出、超时、未配置等行为。核对 JSON 载荷和真实工具效果，拒绝场景必须确认没有执行。

同时核对现有 `pre_tool`/`post_tool`、审批 Reporter 和委派只读边界，确保新事件不制造额外裁决、不扩大允许范围。实际覆盖范围、命令、退出码和未运行项见[rc3 验收记录](../verification/0.150.0-rc3/clippy-approval-hooks.md)及其同名 JSON。
