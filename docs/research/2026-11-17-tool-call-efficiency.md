# agentrules 小改动的工具调用与耗时诊断

日期：2026-11-17。诊断对象：用户截图中 `cursor/composer-2.5` 的 agentrules 发版轮次。只读核对真实会话与 Runtime 工具/任务账本，未调用模型、未重放外部发布命令、未读取凭据。

## 结论

截图中的 76 次工具调用、25 次失败与持久记录完全一致。25 次包括 21 次空参数调用和 4 次项目规则刷新拦截；并非 25 次代码或测试失败。相同参数错误跨 10 个 Provider 轮次出现，没有形成有效纠错。被诊断版本的裸 `rake test` 未被验证识别器接受，导致成功检查仍未进入证据账本，完成门额外要求验证两次，最终 Runtime 状态仍为 `partial`。该识别遗漏已在本轮 rc3 源码修复；原轮次的历史状态不改写。

整轮 354 秒、34 个 Provider 轮次，累计输入 2,383,079 tokens、输出 15,656 tokens。工具执行时间去除重叠后约 22.897 秒（6.47%），约 331.103 秒位于工具执行区间之外。后者包括模型请求、上下文传输、调度和保存等，现有账本不足以逐项精确拆分，不能全部宣称为模型推理时间。输入是累计计量，并非单次上下文大小或费用；缓存占比亦不等于墙钟时间节省比例。

## 调用构成

| 工具 | 调用数 | 缺参数错误 |
|---|---:|---:|
| `read_file` | 21 | 9 |
| `grep_files` | 20 | 12 |
| `edit_file` | 10 | 0 |
| `run_command` | 11 | 0 |
| `git_status` | 8 | 0 |
| `git_diff` | 4 | 0 |
| `git_log` | 2 | 0 |
| 合计 | 76 | 21 |

- 21 次失败的读取/搜索实际参数均为 `{}`：`read_file` 缺 `path`，`grep_files` 缺 `pattern`。错误跨 10 个模型轮次出现。工具没有访问到目标，因此不属于文件慢或搜索慢。
- 4 次 `edit_file` 被项目规则刷新保护拒绝，返回明确的“未执行”。生成 `CLAUDE.md` 会改变适用规则；同批后续写入应暂停，刷新规则后再做。不能通过关闭规则保护来消除计数。
- 另外有 2 次 `rake test` 退出码为 1，但命令工具正常执行，所以没有计入上述 25 次工具错误。首次因 `GENERATED_CLAUDE.md` 未同步；第二次因现有架构文档仍为旧版本。TUI 的失败数与测试失败数目前口径不同。
- `rake test` 共执行 6 次：2 次失败、4 次通过。最后两次由 `[completion-verification-required]` 直接要求，第二次发生在前一次成功后且没有新增写操作。
- 该轮 76 个返回总量为 87,542 bytes，最大单项 11,277 bytes。累计 2.38M 输入不能简单归因为某个超大工具返回；多轮携带既有历史同样会放大输入。

## 已确认的实现缺口

1. **验证命令识别遗漏（已修复）。** 诊断时 [verification.rs](../../crates/willdeep-core/src/tools/verification.rs) 的 `is_verification_command` 列出 `bundle exec rake test`，未列出裸 `rake test`；`accepts_verification` 只接受内置识别或显式配置命令。本轮 `required_verifications=[]`，最终 `verification_evidence=[]`，与两次完成门重复提示、最终 `partial` 一致。修复必须保留实际退出码、当前快照、真实执行及 shell 包装拒绝，不把普通命令或启动回执当测试通过。
2. **缺参数失败没有专门收敛。** 当前 [guidance.rs](../../crates/willdeep-core/src/agent/guidance.rs) 主要针对连续只读探索给自然语言提示，没有在本轮阻止反复发送完全相同的 `{}`。建议按工具、缺失字段及参数摘要聚合，首次返回字段级纠错，重复时禁止无变化重放并给出明确受阻结果；不得擅自猜测路径或替模型执行写操作。
3. **规则刷新与写批次编排有浪费。** [agent.rs](../../crates/willdeep-core/src/agent.rs) 正确拒绝在规则变化后继续执行旧批次。模型在修改生成规则入口时仍安排同批后续写入，造成额外往返。应在规则生成后结束该批并显式刷新，而非削弱保护。
4. **失败统计不能解释失败性质。** [narration.rs](../../crates/willdeep-cli/src/tui/narration.rs) 汇总失败标记，没有区分参数不合法、保护拒绝、执行失败、验证失败。需要保留原始状态，同时提供可展开的原因分类，避免把合法拦截与测试错误混为一谈。

## 尚不能断言的事项

- 持久会话保存了 `{}`，没有保存此次上游原始响应或完整流片段。当前 Chat Completions 流解析代码逐段拼接参数，检查合法 JSON 对象；`{}` 在 JSON 层合法，但不满足这两个工具的必需字段。仅凭最终记录不能判断是模型直接输出、网关规范化还是其他协议适配环节丢参。
- 下一步应使用不含凭据的协议夹具复现 `cursor/composer-2.5` 的实际返回形状，并比对适配前后参数；不能直接归咎模型，也不应先通过换模型掩盖接口问题。
- 用户要求发 `0.28.32`，最后答复和实际发布命令使用了 `0.28.33`。这也是应核对的任务约束偏移，不能把成功推送等同于完全满足原始请求。本诊断未撤销或改写该仓库的提交、tag 或发布状态。

## 改进优先级与验收

先修裸 `rake test` 的证据识别和同类缺参数错误收敛，再对照原始协议验证是否存在参数丢失；之后改规则刷新批次编排与失败分类。目标是减少没有新增证据的模型往返，而非统一放宽验证、限制一切任务到固定调用次数，或仅隐藏失败。

使用离线脚本 Provider 与独立临时工作区回归：合法参数不丢失、缺参不会执行、重复同类错误有界结束；裸 `rake test` 成功后可在相同快照正常完成，失败或快照变化仍拒绝完成；规则刷新后后续写入不使用旧规则；分别报告调用数、错误类别、模型轮次、重复次数与耗时。真实网关联调、付费模型成绩和速度提升数值目前未验证。

## 新增证据：普通身份提问被旧验证任务接管

同一会话后续明确收到新的 `operatorInput`：“你是谁”。持久记录中，模型第一次已正确回答身份；紧接着宿主注入 `[completion-verification-required]`，要求检查当前工作区并继续未完成任务。此后执行了两次 `rake test` 和一次 `git_status`，最终回复被发版校验结果覆盖。截图显示本轮耗时 25.38 秒、工具 3 次；这些调用并非回答身份所需。

诊断时 `CheckpointRecorder::initialize_verification` 采用旧检查点基线优先的 `previous.or(current)`；同会话新输入仍使用会恢复所有非 Completed 检查点的 sink。上一轮 partial 因而可把旧基线带入新轮次。该问题与裸 Rake 识别遗漏叠加，前者触发不必要验证，后者让已成功的验证不能收口。不能将截图解释为模型起初没有理解提问，或解释为所有问答都应测试。

正确边界：普通新输入独立建立本轮验证范围；历史未验证状态保留，不据此宣称旧任务完成。同任务恢复则继续保留原基线、失败证据、显式完成契约与未知副作用。该修复已进入 0.152.0-rc1 源码：限定 Core 检查 78 通过、0 失败、1 个由父测试调用的子进程入口忽略；CLI 与本地 TUI 两个入口检查通过。离线合成 Provider 已验证真实修改留下 partial 后，纯问答 0 工具、1 次 Provider 请求即完成，旧任务仍未完成；复用 Agent、真实新修改、replay/host/Goal、完成契约与未知副作用均保留门禁。最后的元数据加固由 Core 限定检查覆盖。新增 `run --continue-task` 明确继续旧任务，必须绑定已有会话；普通 `run --session` 继续使用新输入范围。修后 CLI 4 项、真实 headless 3 项通过，含默认 Runtime 向同一个未竟 Session 提交“你是谁”的反向检查：1 轮、0 工具、旧 Partial 与必跑检查保留；原重启恢复和单次写入断言也保留并通过。最终工作区组合仍待完成；不按提问关键词豁免。

## 本轮已实施的最小修复

rc3 完成验证门加入裸 `rake test`，同时拒绝裸命令与 Bundler 形式的 dry-run、任务列表、execute-only 模式及 shell 包装。新增两个回归先实际失败（同组 23 通过、2 失败），修复后验证账本 25 项通过、0 失败、0 忽略；覆盖失败退出、成功入账及后续快照变化失效。实际 Rake/网关整轮与速度提升尚未测量，不把单元测试等同于原会话重跑。

配套统计见 [JSON](2026-11-17-tool-call-efficiency.json)。重复空参数收敛、规则刷新批次编排、失败分类和原始协议取证仍未实施，不宣称整体调用数或失败率已经下降。
